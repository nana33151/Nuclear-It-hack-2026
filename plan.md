Оффлайн-межкамерный трекинг по ТЗ Нтехлаб (3 человека, 2 дня)
Сложность: STANDARD. Для хакатона хватит Composer 2.5 / Grok medium; правила склейки и порог T лучше сверять более сильной моделью.
Источник требований: [ТЗ на хакатон_v2](/home/yana/Документы/html/images/ТЗ на хакатон_v2.docx.pdf). Пример данных: Яндекс.Диск.
Что фиксирует ТЗ
Цель: сквозной трек человека, пока он виден хотя бы одной камерой. Трек — непрерывный фрагмент движения; может начаться на одной камере и продолжиться на другой.
Правило ID (обязательное для жюри):
* ID принадлежит эпизоду видимости, не человеку.
* Краткий пропуск на одной камере не закрывает трек: можно опираться на соседние кадры и другие ракурсы.
* Нельзя склеивать два фрагмента только потому, что «это тот же человек», если он полностью исчез из всех ракурсов на длительный период.
* Повторный вход после закрытия — новый ID. Число треков может быть больше числа людей.
* Ручная расстановка ID на проверочном видео алгоритмом не считается.
Что дают организаторы (не нужно угадывать):
* офисные видео с нескольких камер;
* идентификаторы камер и описание зон обзора;
* план офиса и расположение камер;
* синхронная запись: временное смещение пренебрежимо мало.
Что разрешено / что писать самим:
* Разрешено: любые открытые детекторы людей или силуэтов, готовые однокамерные трекеры, готовые ReID-веса как признаки.
* Команда сама реализует объединение между камерами и определение начала/конца сквозного трека.
* Готовый чёрный ящик MTMC end-to-end не использовать. Идеи и код ассоциации (кластеризация, матрица расстояний) пишем сами; чужие пайплайны вроде Yachiyo/vehicle_mtmc — только как справочник алгоритма.
* В описании решения указать библиотеки/модели и явно отделить, что сделала команда.
Оффлайн: предварительная обработка разрешена, realtime не обязателен.

Общий контракт (день 1 утро, все трое)
Один формат, иначе UI и отчёт разъедутся.
* Детекция / силуэт: camera_id, frame_idx, timestamp, bbox, score, mask (RLE или путь), опционально keypoints, usable_for_reid.
* Локальный треклет: camera_id, local_id, t_start, t_end, боксы по кадрам, средний ReID-вектор, цвет верх/низ по маске, кадр-представитель.
* Глобальный трек: track_id, t_start, t_end, куски {camera_id, local_id, t_start, t_end}, cameras[], причина закрытия gap_exceeded.
* Топология из данных организаторов: зоны обзора и допустимые переходы камера→камера. План офиса и расположение камер — вход для доп. карты и опциональной гомографии пола.
* Отчёт сдачи: JSON/CSV со всеми треками + одно число n_tracks.
Готовые компоненты на старте (без обучения):
* Силуэт и бокс: yolo11x-seg.pt (класс person). Отдельный yolo11x.pt не обязателен, если seg даёт и маску, и бокс.
* Поза для отбора кропа: yolo11x-pose.pt (по желанию).
* Цвет одежды: SCHP ATR/LIP (schp-atr-18).
* Однокамерный MOT: ByteTrack или BoT-SORT. BoxMOT удобен, но AGPL-3.0 — для закрытой сдачи лучше чистый ByteTrack.
* ReID: SOLIDER Swin-B (репозиторий); запасной CLIP-ReID. Это признак для нашей склейки, не готовый MTMC.
Своя склейка (человек 3):
* Матрица: 1 - cosine(ReID) + расстояние цвета одежды + запреты по времени и зонам.
* Ассоциация: average-linkage / жадный матчинг с порогом. Справочно: vehicle_mtmc, wda_tracker, идеи Yachiyo OSC — реализуем сами.
* Рождение: первый момент видимости в любой камере. Смерть: нет наблюдений ни на одной камере дольше T. Закрытый ID не переоткрывается.
Гомография / карта:
* План и расположение камер уже в данных — ветка не «если повезёт», а доп. задача ТЗ.
* Базовый путь склейки не ждёт идеальной калибровки: зоны + время + ReID уже обязательны.
* Для положения на плане: гомография пола по углам комнаты / опорным точкам в зонах камер, точка человека = низ бокса. На карте отдельно рисовать наблюдаемый сегмент и пунктир вне FOV.
Человек 1 — силуэты и признаки кадра
Зона: видео → детекции с масками. Треки не собирает.
* Прогон YOLO11-seg по всем камерам, класс person, низкий порог (~0.25).
* SCHP по кропу: маски верха/низа, цветовые гистограммы.
* Опционально YOLO11-pose: отбраковка обрезанных/мелких кропов → usable_for_reid.
* Выход: таблица детекций + кропы. На одном ролике проверить, что силуэты стабильно находятся.
Не делает: MOT, ReID-обучение, межкамерные ID, UI.
Человек 2 — однокамерный MOT и ReID
Зона: одна камера, локальный непрерывный кусок. Готовые веса ReID.
* ByteTrack/BoT-SORT на таблицах человека 1.
* Короткие дыры внутри одной камеры (T_local << T) сшиваются; это ещё не глобальный конец.
* SOLIDER только на usable_for_reid. Вектор треклета = среднее L2-нормированных эмбеддингов + медианный цвет верх/низ.
* Высокая внутритрековая дисперсия эмбеддинга → резка треклета.
* Выход: треклеты по контракту. Локальная проверка непрерывности ID на одной камере.
Не делает: сравнение камер, глобальный ID, UI.
Человек 3 — склейка, отчёт, UI, карта
Зона: главная поставка по ТЗ. Склейку пишет сам.
* Кандидаты только из связанных зон и допустимого окна перехода (из описания зон / плана).
* Склейка по ReID + цвет + время; порог MIN_SIM и разрыв T подобрать на фрагменте демо-видео.
* track_id не переиспользовать после закрытия.
* Артефакт: n_tracks и перечень треков с камерами и временем.
* UI (обязательно): два+ синхронных видеопотока, оверлей силуэта и глобального ID, счётчик, карточка выбранного трека (камеры + интервалы). Стек любой быстрый: Streamlit / Gradio / простой FastAPI+HTML.
* Карта (доп.): трек на плане офиса; сплошная линия в зонах камер, пунктир вне обзора; при наличии гомографии — точка ног на плане.
* В README: какие модели готовые, какая логика своя, пример ошибки (например, два человека в одинаковой одежде в соседних зонах или долгая окклюзия короче T).
Не делает: обучение детектора/ReID с нуля.
