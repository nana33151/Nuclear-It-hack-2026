Оценка идей и дополнительные предложения по улучшению межкамерного трекинга.Текущий пайплайн (ReID + цвет одежды + hard-флаг доступности камер + эвристики) — типичный и разумный baseline для офисной системы. Основные слабые места таких схем: хрупкость к похожей одежде/освещению, ложные срабатывания на отражениях (зеркала, ТВ, стекло), отсутствие сильных геометрических/временных ограничений и ручная настройка порогов.Оценка предложенных идей1. Обучить ML-модель для решения «тот же ID / не тот же»

Идея правильная и перспективная (многие SOTA-подходы используют learned association: graph neural networks, transformers, hierarchical clustering с learned costs). Но отсутствие размеченных данных — реальный блокер. Полная ручная разметка tracklet-to-tracklet пар дорогая и скучная.Практичные варианты без полного labeling:
Weak supervision / semi-supervised: использовать текущие эвристики + высокий порог уверенности как псевдо-лейблы, потом итеративно улучшать (active learning на самых сомнительных парах).
Unsupervised / self-supervised association: clustering tracklets по appearance + spatio-temporal features, потом обучать модель различать positive/negative пары.
Синтетика + domain adaptation (если есть возможность генерировать правдоподобные офисные сцены).
Начать с простой модели (градиентный бустинг / небольшой MLP / даже logistic regression) на фичах, которые уже есть (ReID cosine, color hist, time delta, camera pair, estimated velocity и т.д.), а не сразу глубокую сеть.
Это хорошая среднесрочная цель, но не первое, что стоит делать.2. Математическая модель офиса + проекция tracklets «на потолок» (ground-plane / BEV)

Отличная и очень практичная идея. Именно геометрические ограничения лучше всего бьют отражения, ложные детекции на экранах/зеркалах и физически невозможные переходы.Стандартный подход:
Калибровка (хотя бы грубая) камер относительно пола / общего плана офиса → homography на общую ground plane (bird’s-eye view).
Проецировать нижнюю точку bbox (или центр ног / footpoint) на эту плоскость.
В BEV-пространстве проверять:
Совпадение позиций (с учётом погрешности калибровки).
Непрерывность траекторий и разумную скорость.
Невозможность «прыжков» сквозь стены / мебель (если есть простая карта препятствий).
Фильтрацию точек, которые попадают в зоны, где человек физически не может стоять (стены, столы, зеркала, ТВ).

Даже приблизительная калибровка (ручные точки соответствия + refinement по реальным трекам) уже сильно помогает. Многие современные multi-camera системы (ReST, методы с hierarchical GNN, anchor-guided clustering + spatio-temporal consistency) активно используют именно spatial association в общем координатном пространстве. Это один из самых high-ROI шагов именно для вашей проблемы с отражениями.Дополнительные идеи (по приоритету и сложности)Высокий приоритет / относительно быстро внедряемые
Жёсткие и мягкие spatio-temporal constraints.
Матрица переходов камера→камера с окнами времени (min/max travel time), возможными путями и вероятностями. Обрезать невозможные ассоциации до стадии ReID. Добавить проверку скорости/направления после проекции на ground plane. Это классика и сильно снижает combinatorial explosion.
Улучшение cost matrix и matching.
Вместо простых порогов — взвешенная стоимость:
cost = α * (1 - ReID) + β * color_dist + γ * time_penalty + δ * spatial_dist_BEV + …
Дальше Hungarian / greedy / hierarchical agglomerative clustering / multi-cut. Добавить temporal smoothing и multi-hypothesis (не сразу убивать альтернативные гипотезы).
Лучшая работа с tracklets.
Не матчить одиночные детекции, а целые tracklets (mean/aggregated ReID-фича, длина, стабильность, скорость). Использовать quality-aware aggregation (больше вес качественным кадрам). Hierarchical clustering tracklets с проверкой consistency.
Фильтрация отражений без полной 3D-модели.
Помимо ground-plane: проверка высоты bbox (отражения часто имеют другую перспективу/размер), анализ движения (отражение в зеркале/ТВ часто имеет другую кинематику или «привязано» к статичному объекту), проверка, лежит ли проекция в зоне, где ожидается реальный человек.
Средний приоритет
Более сильные appearance-фичи.
Не только глобальный ReID + цвет. Добавить part-based / local features, pose/gait cues (если есть pose estimator), clothing attributes. Camera-aware нормализация (уменьшить domain gap между камерами). Современные unsupervised/self-supervised ReID-модели иногда дают хороший буст без вашей разметки.
Graph-based / learned association.
Построить graph, где узлы — tracklets/detections, рёбра — возможные ассоциации с costs. Решать через GNN, lifted multi-cut или transformer association module (есть готовые архитектуры вроде ReST, hierarchical GNNs для 3D/BEV tracking). Можно начать с классических graph methods без обучения.
Online vs offline / global association.
Если latency позволяет — периодически делать global re-association в окне (несколько секунд/минут), а не только online handoff. Это чинит накопленные ошибки.
Долгосрочные / более тяжёлые
Полная 3D-реконструкция / multi-view 3D tracking (если камеры хорошо перекрываются и есть калибровка).
End-to-end learned multi-camera tracker (detection + association jointly).
Active learning pipeline: система показывает оператору самые сомнительные ассоциации для быстрой разметки.
Использование дополнительных модальностей (если появятся): Wi-Fi/Bluetooth, двери/турникеты, audio.

Пока трек Unconfident — не назначаем ему глобальный межкамерный ID и не отдаём наружу как готовый объект (или отдаём с флагом «low confidence»).

Назначение нового глобального ID
Новый глобальный ID выдаём только при переходе Unconfident → Confident и при отсутствии хорошего матча с любыми живыми (Confident + Lost) треками из других камер.

Потеря трека (Confident → Lost)
Если трек не смэтчился M кадров подряд → переводим в Lost.
В состоянии Lost:
Продолжаем обновлять позицию по Kalman (или более умному предиктору).
Держим appearance-фичи (ReID + цвет) для возможного re-identification.
Можно понижать вес старых appearance-фич (exponential decay).

Время жизни в Lost обычно 1–5 секунд (зависит от типичного времени перекрытия и скорости людей в офисе). Для межкамерного сценария иногда держат дольше (до 10–15 сек), если человек мог уйти в слепую зону между камерами.

Смерть трека (Lost → Died)
По таймауту (время в Lost превысило порог).
Или по явным геометрическим признакам: трек ушёл за край кадра в направлении выхода из зоны покрытия системы, или его проекция на ground plane ушла в «запрещённую» зону.
После Died трек больше никогда не участвует в матчинге.

Важные дополнительные механики
Age / hits / time_since_update
Классические счётчики:
hits — сколько раз успешно смэтчился.
age — сколько кадров существует.
time_since_update — сколько кадров не обновлялся.
По ним удобно задавать все пороги.

Разные пороги для разных переходов
Порог матчинга (ReID + цвет + spatial) для Unconfident треков обычно делают строже, чем для Confident/Lost. Новому треку сложнее «перехватить» ID.
Межкамерный аспект
Когда трек в одной камере уходит в Lost, его appearance и последняя BEV-позиция должны оставаться доступными для матчинга с новыми треками в соседних камерах (с учётом camera transition matrix и времени перехода).
Именно поэтому важно не убивать трек слишком быстро.
Защита от ID-switch при рождении
Если новый Unconfident трек хорошо матчится с недавно Lost треком (даже из другой камеры) — лучше реактивировать старый, чем создавать новый.
Типичные значения параметров (стартовая точка)
Подтверждение: 3–5 кадров (при 15–25 fps).
Переход в Lost: 5–15 кадров.
Время жизни Lost: 1.5–4 секунды (можно сделать зависимым от камеры/зоны).
Минимальный hits для выдачи глобального ID: 4–8.
Что ещё стоит добавить
Quality-aware confirmation — учитывать не только количество кадров, но и качество детекций (confidence детектора, размер бокса, отсутствие сильных окклюзий).
Duplicate suppression — если два Unconfident трека очень близко и имеют похожую внешность, один из них можно сразу убить.
Exit zones — явные зоны выхода из системы (двери, края покрытия), при попадании в которые трек быстрее уходит в Died.
Логирование причин смерти/рождения — очень помогает потом анализировать, почему появляются лишние ID.
В целом предложенная схема с четырьмя состояниями — хорошая и рабочая. Главное — сделать переход Unconfident → Confident достаточно строгим и никогда не выдавать новый глобальный ID, пока трек не подтвердился и не проверил отсутствие матча со всеми живыми треками (включая Lost из других камер).Хочешь — могу набросать более формальную state-machine (псевдокод переходов) или таблицу приоритетов матчинга в зависимости от состояний.
